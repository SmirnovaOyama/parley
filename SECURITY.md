# Security

Parley stores other people's API keys and chats, so security reports matter a lot.

## Reporting a vulnerability

Please don't open a public issue. Report it privately through GitHub: [report a vulnerability](https://github.com/SmirnovaOyama/parley/security/advisories/new) (the repository's **Security** tab). Say what you found, how to reproduce it, and what someone could do with it. You'll get a reply within a week, and credit in the fix if you'd like it.

Supported versions: the latest commit on `main`.

## Things worth knowing when you deploy

- `KEY_ENCRYPTION_SECRET` encrypts every stored API key. Keep it out of the repository and out of backups stored in the same place as the database.
- Run Parley behind HTTPS. Session cookies are `Secure` and `HttpOnly` in production.
- The first account to sign up becomes the admin. Sign up as soon as the site is up, and turn off sign-ups if it's public.
- Admins can make the server connect to any address (keys for "another service"), and can read every chat. Only give the admin role to people you trust with both.
- Every other key goes only to its provider's own address, whatever the server's environment says: `ANTHROPIC_BASE_URL`, `OPENAI_BASE_URL`, `ANTHROPIC_AUTH_TOKEN`, `OPENAI_ORG_ID` and `OPENAI_PROJECT_ID` are never read.
- Someone with an account could try to turn it into a relay that passes the site's keys on (a reverse proxy on their sign-in). Changes through the API must come from the site's pages in a browser (`Origin`, and `Sec-Fetch-Site` where sent), each person can have three replies written at once and send 20 messages a minute and 200 an hour, and each account can be signed in on a limited number of devices (5 unless an admin changes it). Those headers can be faked, so the limits are what really hold: set a spending limit for members, and look at where people are signed in (on their page under Admin → People) when one has many devices, many networks, or a program instead of a browser.
- An MCP server on one shared account is called with the headers an admin enters, for everyone allowed to use it, so they all act with those credentials. Give it a token with only the rights all of them should have. Turn on "Tell it who's asking" for a server that should tell people apart: every request then carries the person's email in an `X-Parley-User` header, which the server can trust only as far as it trusts Parley's token.
- An MCP server on each person's own account is called with that person's own sign-in or token and nothing else: not the admin's headers, and not anyone else's account. People who haven't connected can't use its tools. Their tokens are encrypted with `KEY_ENCRYPTION_SECRET` like API keys, so whoever runs the server, with the secret and the database, could still read them: this stops everyone acting as the admin, not the people running Parley from reaching your account. Tokens are forgotten (and withdrawn from the sign-in service, where it offers that) when the person disconnects, loses access to the server, is turned off, or an admin changes the server's address or way of signing in, disconnects everyone, or removes it. Admins see who has connected, never their tokens.
- Signing in follows MCP's authorization spec: PKCE, a `state` tied to the person who started the sign-in and good for ten minutes, and tokens bound to the server they're for. Addresses the server names for signing in are fetched only if they're on the public web, unless they're on the server's own host. Set `PUBLIC_URL` when a proxy in front of Parley changes its address, so sign-in services send people back to the right place.
- Tools bring in text other people wrote: web pages, search results, shared knowledge, MCP results. Any of it can carry instructions aimed at the model. Parley fences it off as outside content, and asks the person on a line in the chat before it reads a page whose address the model didn't get from their messages or a search, keeps a memory note once the chat has taken in a page, file or tool result, or runs an MCP tool that may change things. Under Admin → Tools, every tool an admin lets run without asking is one an injected instruction can run, so keep that to tools that only read and don't reach other services.
- What an MCP server says about its tools (descriptions, inputs, and whether they only read) goes to the model in every new chat that has them. Parley takes it as written only when an admin adds the server (for one people sign in to, at the admin's first sign-in). Listed again later, or reached at a new address or with new headers or a new token, tools that are new or read differently wait under Admin → Tools, each beside what it said before, until an admin uses them or keeps the old ones; chats already started keep the tools they started with. Once used, new words reach every new chat, so read them for instructions that don't belong there first.
